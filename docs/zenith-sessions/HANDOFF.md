### Exact destinations and the batch queue

- `RobloxDestinationParser` and `RobloxRequestedDestination` carry a positive 64-bit place ID and, where resolved, a canonical job ID and server kind. Keep unresolved share, follow, private, or reserved destinations explicit. A requested link alone does not establish current presence, permissions, available slots, or arrival.
- The UI handoff is [LaunchCoordinatorBatches.cs](../../src/Zenith.Sessions.Core/LaunchCoordinatorBatches.cs). Call `CaptureBatchReview(destination, recipients)` to freeze one destination plus the selected profiles, revisions, priorities, and account bindings. Submit the resulting review once with `EnqueueBatchAsync(review, ct)`. The review belongs to its original queue. Panic fences stale reviews. Accepted rows share one durable queue write.
- `CaptureBatchRetryReview` takes retained failed operations, current profiles, and current bindings for the same Roblox players. It preserves the original destination: one exact server, or one place with no server when every request in the review chose that place. It only accepts a `Failed` row with no process receipt whose start was rejected or whose preparation was refused or expired before dispatch. Successful accounts stay in place. An uncertain or possibly live client must be reconciled separately. The result reports per-account dispositions such as `AlreadyPending` and `RetryNoLongerEligible`. Queueing and retry preserve the queue's pause state.
- `ShellDirectoryFeatures.QueueFrozenRecipientsAsync` now uses this batch path for both the checked-accounts and saved-bundle routes: one review, one durable queue write and one queue update per request, with the per-account dispositions mapped to the existing queued/blocked/already-pending summary. A stopped queue rejects the whole review with nothing written. Leaving the page or locking after the commit still withdraws the rows that request created. The explicit review and Cancel/Panic behavior are unchanged. The single-account Queue command keeps the per-request `EnqueueAsync`. [Batch and retry verification](DESTINATION-DRAFT-VERIFICATION.md#backend-055-exact-batch-commit)

### Process, player, and server evidence

- `WindowsSessionLogCorrelator` bounds discovery, file reads, and holder checks. `SessionEvidence` separates current facts from last-known facts and fences replay, file replacement, partial lines, an unread log tail, and competing ownership. `NativeTrialEvidence` projects fresh process presence and reported player/place/job values for review.
- Launch-to-log: `NativeRobloxHandoff.Capture` keeps the validated browser tracker as its own number (never the URI). It travels beside the process receipt into `LaunchProcessReceipt.BrowserTrackerId`. A queue holding one is saved as format 8; other queues stay format 7. `WindowsSessionLogCorrelator` reads bounded log heads (64 KiB, lines before the first join) and reports a `LaunchLogLink` per launch, separate from the holder binding. That link survives a client restarting under a new PID. It is corroboration only and proves neither the account nor arrival. The tracker line shapes are unverified against a real client.
- Reported matching IDs remain diagnostic. Hold that boundary when wiring the new UI. Use separate statuses for requested destination, observed local process, reported player/server, and verified arrival. Never route input from a manual profile label, PID alone, file order, or uncorroborated log claims. [Tracking verification](NATIVE-TRIAL-EVIDENCE-VERIFICATION.md#backend-054-log-tail-coverage)
- Since 2026-11-08 (R-launch-2, owner decision) one advisory use of that diagnostic evidence exists, off by default: with Settings → Performance profile → "Shorten the wait between starts when the previous client reports it joined" saved on, a Connected log entry for exactly the started client's receipt (PID and creation time) may end the startup stabilization wait early through `LaunchCoordinator.ReleasePacingEarly`, never below the launch spacing and never past the full stabilization.
