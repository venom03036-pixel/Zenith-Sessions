# Optional master password and portable backup

Approved scope: R-accounts-10, R-accounts-11/R-shell-18; VA-03-01–04, VA-08-01/02/05/06, VA-10-02 and PROD-QA-07. This is the separately reviewed design required by VA-08-05 and Rule 20. EFS is independent. Existing metadata-only export and DPAPI storage remain the defaults. No new cryptographic dependency is introduced.

## Master-password format and migration

Existing v2 credential envelopes keep their DPAPI CurrentUser payload. V3 adds AES-256-GCM around those existing DPAPI ciphertext bytes under a random 32-byte vault data key. The associated data includes the envelope format, key identity and selected local profile identity. The old authenticated inner payload continues checking provider/user/generation/context against metadata. A clear metadata envelope remains available to list accounts without decrypting their credentials.

A versioned, atomically written control file protects the data key using CurrentUser DPAPI. When password mode is on, the ONLY persisted data-key copy is AES-GCM wrapped using a PBKDF2-HMAC-SHA512 password key (600,000 iterations, a fresh 32-byte salt), then DPAPI protected. There is no alternative DPAPI-only recovery copy. When the user explicitly disables password mode after authenticating, the control record may contain the DPAPI-only data key again. Format/mode/key/KDF fields are authenticated by the protected control record and AES associated data; parsing imposes strict byte, field and KDF bounds before derivation. Passwords are bounded UTF-8 buffers, not settings, diagnostics or immutable model properties.

The first enable operation takes the existing in-process writer and cross-process lease. It durably writes a password-protected `Migrating` control record before changing existing v2 records. All normal secret reads/writes are blocked while migration is incomplete, including the legacy v2 read path. Each selected record is validated, wrapped and atomically replaced without changing its profile or authorization generation. Existing exact snapshot digests naturally become stale. Only after the bounded inventory contains no unwrapped credential records or recognized obsolete secret copies does the control record become ready. No older record or key is automatically restored.

A process failure or cancellation can leave a mixed v2/v3 disk inventory, but no ordinary credential operation can consume that inventory. Startup remains locked/migration-required. Explicit same-password resume continues conversion; failed/corrupt records preserve their originals and remain a recovery issue. Previously completed conversions are retained. There is no implicit downgrade, empty-vault replacement, backup fallback or rollback to old credentials. Later mode changes rewrap the data key rather than decrypting every record. Same-user malware while unlocked, administrator access, memory capture and rollback of an entire external filesystem backup remain outside the protection claim.

Lock fences late key installation and new secret use, clears mutable key buffers, and is wired to the existing manual/Windows/idle lock. A slow unlock completing after Lock cannot reopen the vault. Already acquired authorization material must still be cancelled/joined by its existing owner; managed strings cannot be promised perfectly erased. Account metadata remains accessible, and Panic/safe closure stay available. A forgotten password means these saved sign-ins cannot be recovered; profiles can be retained and signed in again through an explicit removal/recovery operation.

## Portable backup format

Portable backup is a separate action labelled as containing saved sign-ins. Its save dialog and final confirmation explicitly identify that content. It requires an export password and, when enabled, an unlocked master-password vault. It never replaces the default metadata-only export command.

Use a versioned fixed header, 32-byte salt, 12-byte random nonce, AES-256-GCM tag and PBKDF2-HMAC-SHA512 at 600,000 iterations. Authenticate the entire header as associated data. Reject unknown versions, noncanonical lengths, unsupported KDF parameters, oversized files and oversized decoded collections before allocation/derivation. The output contains no DPAPI layer, because portability is explicit, but all bytes written to disk after the public header are encrypted. Serialize to bounded memory, seal it, then atomically write ciphertext-only temporary output; clear mutable plaintext/key buffers in every exit path. Do not write plaintext JSON intermediates.

The payload includes profile metadata, saved group names/colors/order, favorite destinations, an allowlisted settings snapshot and reusable Roblox-session records. Exported profile IDs are only mapping labels. Export takes coherent bounded snapshots; concurrent profile/grant changes produce a retry-required result rather than mixing old and current credential generations silently. No launch ticket, transient access token, native process receipt or current browser state is included.

## Import merge and authority

The user selects a backup and supplies its password, then reviews importing into the current library. Successful decryption is not authorization proof. Imported profiles receive fresh local GUIDs and revisions; source IDs only map metadata to proposed sign-ins. Source authorization generations are never adopted. Groups merge by canonical name, with existing local group configuration taking precedence; new groups append in exported order. Favorite destinations are validated and appended using fresh local IDs, with exact existing destinations retained rather than overwritten.

Allowlisted settings are ordinary appearance/density, view/window-layout preferences and conservative performance/capacity preferences, validated by current settings rules. Apply them only through an explicit settings-import choice and the existing settings writer. Do not import launch qualification records, publisher acceptances, executable paths, auto-start/auto-launch state, queue operations, active macro/broadcast state, Discord/webhook secrets, remote credentials or machine-bound identity. Default import leaves automation stopped and existing local security/idle-lock/Panic settings intact.

For each candidate session, the existing Roblox session client must authenticate it as exactly the exported verified player. Import uses the link service's current per-operation ownership and snapshot/generation commit fences. Existing local sign-ins, including newer generations for the same player, are kept; no backup record overwrites them. Identity mismatch, cancellation, expired sessions and conflicts leave metadata available but sign-in required. Partial success is reported by account count with fixed reason categories; successful imports are not rolled back to prior secret generations. No remote sign-in or real account is exercised during offline tests.

## Validation and review gates

Master-password tests must cover default v2 compatibility, wrong password, locked reads/writes/dispatch, no alternate persisted key, swapped/tampered headers and profile ciphertext, interrupted conversion, explicit resume, missing/corrupt control files, late unlock after Lock, mode changes and zeroed owned buffers. Existing snapshot, claims, generation, cleanup and multi-process tests must still pass.

Portable tests must use synthetic cookies and a fake identity client: round-trip across independent fixture roots, header/KDF bounds, wrong password/tamper, ciphertext-only temporary artifacts, all specified metadata categories, fresh destination IDs, ignored unsafe settings/qualification data, same-player existing sign-in preservation, mismatch/conflict/cancellation fences and exact reported partial outcomes. Final source review must independently inspect secret lifetimes, migration recovery, format authentication, UI consent and import authority before live fixture trials. [Master-password implementation evidence](MASTER-PASSWORD-VERIFICATION.md) is now separate; portable backup remains planned and unverified.
