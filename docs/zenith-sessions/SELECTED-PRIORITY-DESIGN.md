# Selected client priority and stopped-arrival publication

Cycle 0.49 increment follows the verified 0.48 request flow. It adds an actual Windows process control and repairs a final launch publication race. Native account association and independent background execution remain separate acceptance work.

## Selected process control

Sessions offers Normal, Below normal and Restore original for the explicitly checked clients, falling back to the selected row. Pin at most 128 unique PID/start identities from the current complete inventory before asynchronous work. A process Windows would not open, such as another Windows user's client, appears as an identity-unavailable row (no start time) and makes the monitor call the scan incomplete; that row is skipped instead of blocking every selection, though its PID still counts in the duplicate check, and selecting it is refused with that reason. Trim now uses the same pin. Refresh the process identity immediately before reading or changing it. No account label substitutes for process identity.

One backend owns a serial mutation lane and a bounded in-memory map of original and last-applied priority. A native handle is short-lived and checked for the exact PID/start, current Windows user and RobloxPlayerBeta executable. Use only the required query/set rights. Normal and Below normal are the only requested classes. Refuse an existing class outside those supported settings rather than changing it. Confirm the readback after an accepted set, even when cancellation arrives, and preserve a truthful partial result. Cancel prevents later mutations. Restore changes only a still-matching process whose current priority equals the last setting applied by this owner. An observed conflicting external change is reported and preserved. An already restored original is acknowledged without another write. Windows provides no atomic compare-and-set, so a simultaneous external change can race the final check.

The UI reports each outcome and pending restore ownership. Lock and Panic cancel current changes. Exit cancels and joins work, then attempts to restore the owner's outstanding settings through the same lane. A crash or refused Windows operation can leave an applied setting until that process exits or is changed explicitly, and the interface and guide explain this. Exit reports any remaining restoration failure before closing. No profile, account credential or startup automatic application is added.

Changing scheduling priority does not establish lower memory use, FPS control, CPU percentage cap or additional client capacity. Its benefit still needs equal-workload measurement. Microsoft documents the process access requirements and scheduling semantics. [SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass), [GetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getpriorityclass).

## Arrival publication

After an arrival confirmation finishes, retain the same serialized boundary for verifying the active operation, stop generation, paused state and cancellation and for publishing its next state. Panic or Stop cannot be overwritten by an old Arrived result queued behind storage work. Retain already observed process receipts and uncertainty reservations. Test with a controlled supported provider and gated persistence, without promoting the native provider or diagnostic log authority.

## Rules 18 and 20

The changes reuse the shared process inventory and existing view-model lifecycle. There is no new poller, capture owner, input pipeline or dependency. All native work runs off the UI thread, one bounded operation at a time, and actual completion is joined. Original-state tracking is capped at 128 process instances and unresolved ownership is preserved instead of evicted. Failures have typed outcomes and no raw paths or credentials in status.

This is incremental. Existing queue and window behavior, custom settings, saved formats and installed editions remain intact. Tests cover exact identity, denied access, readback, cancellation and restore conflicts, plus the launch stop race. Public and Linux composition do not gain these Personal companion controls. Rollback uses the preceding development files because no data format migration is introduced.

## Efficiency mode and core spreading

Sessions adds Efficiency mode and Spread over cores beside Normal, Below normal and Restore original, for the same pinned exact instances, worker, 128-entry ownership map, Stop, Lock, Panic and Exit paths. Both are explicit per selection and off until chosen. Nothing about the client's files, settings or code changes: only documented process attributes are set from outside, through the handle and rights already used for priority (query limited, set information, synchronize).

Each read takes the priority class, the power throttling masks and memory priority (GetProcessInformation), and the process and system affinity masks (GetProcessAffinityMask). A value Windows does not report, such as power throttling on an older Windows or affinity for a process with threads in several processor groups, stays unknown. Zenith never changes an unknown value, because it could not restore it, and refuses the action that needs it with a plain reason. Normal and Below normal still need only the class.

Efficiency mode sets Below normal, turns on EcoQoS execution-speed throttling while keeping any other throttling bits as found, and sets very low memory priority. Timer-resolution throttling is not added, because it can change a game's frame pacing and was not measured. Spread over cores gives client i of n every nth logical processor of its system mask, so one operation's shares never overlap. It needs two or more clients and two processors for each, and leaves the priority class alone. Normal and Below normal change only the class, so Restore original is the way back from efficiency mode.

Ownership stores every value before this owner's first change and every value it last applied. A later action or Restore proceeds only while all of them still match what Zenith last applied; any observed external change is a preserved conflict. Restore and Exit write back the client's own original values, not Windows defaults. After the final same-handle comparison and Stop check, every differing value for one client is written in a fixed order (affinity, memory priority, throttling, class), so Stop cannot leave a client half changed. A refusal after an accepted write is read back and reported as not confirmed. Ownership then records the values the readback shows as what Zenith last applied, so Restore and Exit return each original value instead of calling Zenith's own partial write a conflict; a change made elsewhere between the write and the readback cannot be told apart and would be restored too. Exit warns about any client it still could not restore. Windows has no compare-and-set for these values, so a simultaneous external write can still race the final check.

Rule 18: at most four extra query calls per read and four writes per client, on the existing single worker, with no new thread, timer, poller or dependency. Ownership entries stay fixed-size and bounded. Failures are typed outcomes without paths or credentials. Tests use the fake native API for apply, readback, restore, unknown values, partial refusal and external conflicts, and two test-owned cmd.exe helpers through the production Windows calls with an independent readback. Enum values are appended and no saved format changes, so rollback is the previous development files. No CPU, memory, FPS or capacity benefit is claimed; it needs an equal-workload measurement. [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation), [GetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessinformation), [SetProcessAffinityMask](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setprocessaffinitymask).

## Client sound

Sessions > Client sound offers Mute and Unmute for the same pinned exact instances, plus an optional saved "Mute clients when they appear" preference that is off by default. It is Zenith's own version of a capability the RoALT reference has; no RoALT code was used. The client's own Windows audio sessions are changed from outside through the public Core Audio API that Volume mixer uses: IMMDeviceEnumerator lists the active output devices, IAudioSessionManager2 enumerates their sessions, IAudioSessionControl2.GetProcessId matches the exact PID, and ISimpleAudioVolume reads and sets the mute. No Roblox file, setting, FFlag or memory is read or written, and nothing is injected.

Each operation holds one process handle with query-limited and synchronize rights only. While that handle is open Windows cannot give the PID to another process, so sessions matched by PID are that instance's own. The handle is checked for the exact PID/start, current Windows user and RobloxPlayerBeta executable before and after each read and write, so a recycled PID is refused. A session shared by several processes is not the client's own and is skipped. A partly muted client, for example a muted one that opened a second session on another output device that started with its sound on, is a preserved conflict for Mute; Unmute, Restore and Exit turn every one of its sessions on and confirm that by readback. A mute's final comparison happens in the same enumeration as the write, and every session of the client is set, so Stop cannot leave it half muted; Windows has no compare-and-set, so a simultaneous Volume mixer change can still race.

Windows may remember a mute for later sessions of the same program, so restore ownership matters. One worker owns a bounded map (128) of exact instances Zenith muted. Unmute, Exit and Restore turn on only that sound, and only while it is still muted, wholly or in part; sound already turned on elsewhere ends ownership without a write. A client that was already muted before Zenith first muted a client in this run is left muted and never owned. Two test-owned helpers of one program showed, on Windows 11 build 26200, that a helper started while another is muted starts with its sound on, but one started after a muted helper exited starts muted because Windows remembered the mute. So a client that started after Zenith's first accepted mute and is found already muted is owned without a write, reported as such, and unmuted on Unmute and Exit; the arrival status counts only clients Zenith will unmute. If Windows cannot confirm every unmute on Exit, Exit shows a warning with the count. Unmute also turns on a client Zenith did not mute, for example one that started muted because Windows remembered a mute, and that is never undone. A client that closes while muted, or a crash, can leave a later client muted; the interface says so and Unmute or Volume mixer turns it on.

With the preference saved on, the dispatcher compares each fresh scan that names every readable client with the previous one. Clients in the first such scan and clients already running when the preference is saved are never arrivals. A new instance is muted once Windows lists its sound, tried again on later scans for at most 2 minutes, then reported as never muted. Panic, Lock and Cancel stop the current change, drop waiting arrivals and pause arrival muting for the rest of the run; Unlock and saving the unchanged preference do not restart it. It resumes only on Resume muting new clients, or when the preference is saved on after being off, and clients the scans saw while it was paused are never arrivals.

Rule 18: one bounded Core Audio enumeration (at most 64 devices and 512 sessions each) per operation on the existing single worker; arrivals ride the existing sample cadence, with no new thread, timer, poller or dependency. Every COM object is released before the call returns. Failures are typed outcomes and the diagnostics journal records only the ClientSound subsystem and the error type. Tests cover the control and adapter over a fake Core Audio and process API (ownership, recycled PID, exit during a read, no sound, partial mute refused by Mute and turned on by Unmute, Restore and Exit, external changes, Stop, refused restore) and the production calls on a test-owned Windows PowerShell helper that loops silence through SoundPlayer, with a recycled-PID refusal, readback, Restore and Exit. The settings field is optional within schema 1, so rollback is the previous development files. No performance benefit is claimed.
