## Connected workflow

Automation now offers **Inspect and prevent launch** for a selected saved account and game-only destination. A separate private WebView seeds only that selected protected session, loads the exact official experience page and asks the user to choose Play. The window labels the saved ID **Expected player ID**, not an observed native identity. Exact-server requests are explicitly outside this first diagnostic; the production target/recipient requirements remain unchanged.

The external-scheme handler sets cancellation first on every callback. It is installed before session seeding/navigation; failure to install it prevents navigation. Main-frame and child-frame guards are separate, and neither resets an existing cancellation. The narrow native-scheme navigation exception can only reach this cancelling handler. Other schemes, pop-ups, downloads and permissions are blocked. There is no shell execution, process-start, input injection, launch-ticket endpoint or client modification in this adapter.

Only fixed field-label flags, bounded counts and the SDK's nullable user-gesture flag survive inspection. The pure policy limits native input to 32 KiB in both characters and encoded UTF-8, 64 fields and 64-character ASCII field names. It rejects malformed encoding/controls, duplicate fields and unexpected context/origin; unknown names and all values are discarded. These are diagnostic shape rules, not a validated current native launch protocol. Results always have `CanLaunch=false`; a synthetic `NativeLaunchPrevented` property is not evidence that an actual browser event was exercised.

The selected saved-session service owns inspection through completion. Before any browser request it durably advances the grant to SignInRequired. The probe is asked first whether it would refuse without opening anything (Busy while this process still holds a private sign-in folder that its owner may yet release, CleanupFailed once its cleanup latch is set or while another owner keeps its folder after a failed cleanup, StorageUnavailable while sign-in storage is known to fail); a refused check returns before that write and leaves the grant Linked, and native preparation does the same before committing its pending grant. An inspection or native preparation for an account whose removal from the library is still running is refused by the saved-session service before any grant is reserved and reported as ProfileRemoved, not Busy: the inspection status says the account is being removed and is recorded as not completed rather than as an error, the native-stage Preparation line says the preparation was refused before the saved sign-in was used or changed, and a Sign in or Refresh on that row is a notice with no SignIn failure record (O-C1-3). Leftover data that admitting the probe's own folder must not open or remove (a folder that is not Zenith's, has no valid marker, is redirected or holds redirected data, holds more than cleanup may inspect, or more leftover folders than one admission may open) latches CleanupFailed instead of reporting a missing WebView2 Runtime, so later checks are refused before any grant is reserved. Any other storage failure during that admission (redirected storage, permissions, a full disk, or a file another program still has open) reports BrowserUnavailable. That check had already reserved its grant, so its account is left at SignInRequired, and the status names WebView2 and the data folder and says to sign in again once storage is fixed; a sign-in refused that way asks for usable storage instead of naming a leftover folder. Admission and the startup sweep remember such a failure per sign-in storage root, in memory only and apart from leftover data kept for review, and a remote data folder is known from its path alone. While either holds, later checks and native captures refuse with StorageUnavailable before reserving any grant, so a queued launch of several accounts costs at most the account whose check met the failure. Native preparation reports that refusal as StorageUnavailable, not CleanupFailed, so the configured provider records a rejected start (which counts toward the queue's repeated-refusal pause) and does not stop native launch until restart. Only a real admission tests the storage again: one that prepares its folder (such as the sign-in the affected account needs, which reserves no saved grant and is never refused for this) or a startup sweep that checks signin-browser-data and leaves no leftover behind lifts the refusal. The refusal does not expire on a timer and is not lifted by a metadata check, because neither can tell that a permission, a full disk or a file held by another program is fixed, and lifting it early would put the next account's saved sign-in at risk again. The startup sweep and every admission also remember, per sign-in storage root and in memory only, leftover data they kept for review; while that reminder stands, a fresh probe or native capture after a restart refuses with CleanupFailed before its first reservation instead of costing an account its saved sign-in, and a later clean admission or sweep clears it. The reminder also covers a sweep that left more folders behind than one admission may open, whatever kept each one (held by another owner, a file still open, or not opened because the run's budget ran out), because the next admission refuses them all. The sweep's result carries that rule itself (`SignInSweepResult.NeedsReview`), and startup reads it for the review event, the credential-cleanup status and the SignIn failure record, so startup never shows only the routine "retries them" or "left for the next sign-in" lines while the checks refuse as a cleanup failure; in that case it says how many folders remain and that sign-in waits until they are reviewed. After a cancelled handoff, the adapter reads only its own current cookie, closes its browser and finishes cleanup before returning the owned credential. The existing fixed authenticated-user check must then verify the same player; accepted rotation, duplicate identity checks, durable generations and identity projection reuse the existing save path. Interrupted, mismatched or failed checks cannot silently reuse the old grant. A postcommit failure can re-fence only this operation's allocated commit generation, preserving unrelated replacements and protected originals.

Lock, Panic, Disconnect, profile removal and Exit cancel/fence future publication and await the actual owner. Selecting another profile/destination cannot retarget an active inspection. The dashboard can report structural capture and renewed saved sign-in; it never reports a native client or arrival. Its in-app Guide and package instructions explain the distinction.

## Ownership, compatibility and review corrections

There is one on-demand browser operation, a three-minute deadline, one sanitized capture and no hidden browser per account. Private folders use the existing marked/leased/ACL-protected storage. Environment overrides are rejected; the installed Evergreen Runtime remains required. The existing sign-in navigation guard is unchanged; only its identical own-cookie extraction moved into a shared helper. No dependency was added.

Actual browser initialization is joined because the SDK provides no cancellation parameter. Cancellation guards stay installed through controller disposal and confirmed browser exit. A five-second cleanup observation timeout returns an explicit fault, retains the real cleanup task/directory owner and blocks another probe; disposal joins that owner. No timeout is treated as proof that native work stopped. Setup failures dispose uninitialized controls and let the outer owner clean the directory. A private folder still leased by another browser owner (such as a sign-in whose browser is still closing) returns Busy before any browser opens; it is not reported as a missing WebView2 Runtime and does not block this probe. A folder whose owner's cleanup failed is different: that owner keeps it and its lease until it is disposed when Zenith closes, so every admission is refused until then. Such a kept folder is counted apart from live owners; the probe, native preparation and sign-in report it as a cleanup failure that needs a restart and, if it repeats, a review of signin-browser-data, never as a busy window to finish or retry. Nothing is latched for it, so once its owner releases it the next admission recovers the folder. The sign-in owner uses the same rule as the probe: after a confirmed browser exit it removes its folder even if cookie deletion failed, and a cleanup that outlives its five-second observation stays tracked, refuses new sign-ins while pending and clears that refusal when the same task removes the folder; disposal joins it before releasing the lease. That cleanup waits at most 30 seconds for the browser's exit: a browser that never reports it would otherwise keep sign-in saying "still closing" and keep Exit waiting for good. Past that limit its guards stay installed, the folder is kept after a failed cleanup (sign-in and the other owners then ask for a restart), and disposal releases the lease while the folder stays marked, so the startup sweep or the next admission recovers it.

Source review found and corrected a missing inspection join during profile removal, an interval that detached guards before controller shutdown, ambiguous expected-ID wording and a pre-cleanup setup failure path. These are source-ordering corrections with controlled surrounding coverage, not reproduced real WebView failures. Native cleanup/event ordering and UI interaction remain unexecuted.

The service's failure safety read followed by generation allocation is **not cross-process atomic CAS**. Tests preserve foreign same-user grants observed before/after this operation's commit, but a truly concurrent replacement between separate storage calls remains a gap. Same-service ownership is enforced. A production dispatch adapter still needs final current-grant/operation-generation authority and an appropriate conditional storage/dispatch boundary; this inspection does not close that requirement.

No macro/container, vault, account DB, settings or queue schema changes occur. Existing Link/Check behavior and legacy authorization formats remain compatible. The previous staged folder is reused; installed editions, actual profiles/credentials, Roblox sessions, Public and Linux remain untouched.
