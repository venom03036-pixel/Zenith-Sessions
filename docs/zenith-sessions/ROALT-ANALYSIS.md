## Current platform-contract research

Official Roblox OAuth describes authorization to Open Cloud resources and identity/API flows, not a saved native-player account handoff. Official account switching describes a manual web feature for up to five accounts. **Inference from the reviewed documentation:** these do not establish the required unattended native selection/process association; this is not proof that every possible compatible provider is impossible. [OAuth overview](https://create.roblox.com/docs/cloud/auth/oauth2-overview), [account switching](https://en.help.roblox.com/hc/en-us/articles/21037888001044-Account-Switching).

The deep-link document identifies `gameInstanceId` as a job target and `userId` as the user to follow, not the identity that should sign in. It also marks that deep-link process deprecated in favor of share links. Zenith can parse a requested public destination while leaving opaque share/private access unresolved; it must not claim a generic link selects a protected saved account or proves arrival. [Roblox deep links](https://create.roblox.com/docs/production/promotion/deeplinks).

For a future independent process/log adapter, Windows Restart Manager reports applications using registered resources and returns process-instance information. **Inference:** a holder observation can corroborate resource use but does not alone prove a particular process authored a log line. Its API errors, bounds and ownership still need implementation/verification. No Restart Manager shutdown/restart is proposed or executed. [RmGetList](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmgetlist). No host RoALT files, raw live Roblox logs or credentials were collected by this increment.

## Pinned guest launch, identity and recovery audit

These are **P-guest source observations**, with true guest line numbers and whole-file fingerprints recorded in the review artifact. They supersede moving-main attribution only for the specific mechanisms and sections listed here. Source comments referring to previous experiments remain **D**; none became a repeated live test in this pass.

- **Account handoff:** `launcher/mod.rs` 139–251 decrypts the selected account's stored cookie, resolves its target, attempts a client assertion, obtains an authentication ticket and constructs a secret native launch URI with a fresh per-launch browser tracker value. Cookie material is reread before authentication calls because the reference expects rotation. `client.rs` 131–155 starts the located executable and closes its initial process handles. A returned PID/start record is launch evidence, not sign-in or arrival. This path depends on cookie/ticket authority; it does not establish an OAuth-to-native handoff compatible with Zenith's saved-grant policy. [Pinned launch](https://github.com/inspectsoftware/RoALT/blob/4d250c0565f5e6daea99797d591c83f76108b916/src-tauri/src/launcher/mod.rs#L139-L251), [pinned process start](https://github.com/inspectsoftware/RoALT/blob/4d250c0565f5e6daea99797d591c83f76108b916/src-tauri/src/launcher/client.rs#L131-L155).

Discovery checks registry/protocol/version locations, excludes Store paths and detects bootstrapper ownership. `update.rs` 139–206 can hold a launch for an update and select an installed production build with a channel override; those are reference-specific launch/update mechanisms, not independently verified compatibility guarantees. Per-launch graphics/settings writes in `mod.rs` 167–209 are additional client mutations, separate from basic dispatch. [Pinned target URI](https://github.com/inspectsoftware/RoALT/blob/4d250c0565f5e6daea99797d591c83f76108b916/src-tauri/src/launcher/uri.rs#L19-L78), [discovery](https://github.com/inspectsoftware/RoALT/blob/4d250c0565f5e6daea99797d591c83f76108b916/src-tauri/src/launcher/client.rs#L23-L118), [launch/update choice](https://github.com/inspectsoftware/RoALT/blob/4d250c0565f5e6daea99797d591c83f76108b916/src-tauri/src/launcher/update.rs#L135-L206).

These are concrete source mechanisms; reviewing them did not execute them or authorize importing them into Zenith. The parser attempts to disregard game-script Output/Warning/Error text. However, `read_new` 166–192 reads the entire appended tail before processing complete lines. A blank mismatch warning must therefore not be described as verified account identity or verified destination arrival. A stored game/follow target therefore differs from a frozen prior-server target. Those are client-enforcement/session-file interventions, not a normal consequence of starting a supported official protocol link. They remain excluded from Zenith under the controlling requirements. Only public source text was inspected; no such behavior or account files were accessed. For an independent compatible provider, keep five capabilities separate: trusted identity linking, selecting that saved identity for a native client, native dispatch, verified arrival and multiple simultaneous clients. The first cannot imply the others. Require an independently supported handoff, immutable selected identity/auth generation and destination, cancellation fences, and exact host/PID/creation identity. A read-only log adapter additionally needs sanitized real-client fixtures, bounded rotation-aware parsing, explicit corroboration of the process/log relationship, positive trusted UserId comparison and fresh place/job observations. File holders, timestamps, labels and log growth alone cannot authorize binding. Stale, ambiguous, unreadable or mismatched evidence stays Unknown; a same-server failure must not silently become successful independent matchmaking. The current production provider remains unavailable, and no live launch, association, arrival, reconnect or sixteen-client acceptance is added by this audit.

The local parser recognizes place IDs, job IDs, usernames/profile targets, Roblox game/deep links and private/share-link forms.
