## Incremental change and compatibility review

An executed pre-fix regression (`manager-0.31-missing-primary-reproduction.trx`) returned an empty queue despite a valid populated orphan backup. Settings has the same first-launch/default reset gap. Source review also found future-version data can be hidden by duplicate top-level version fields in favorites/bundles or treated as ordinary settings corruption, and repair can overwrite older damaged settings evidence.

Repair these existing storage paths incrementally. A valid committed primary stays authoritative. A verified backup may supply missing/corrupt metadata without rewriting on load; recovered queue work is paused and the coordinator keeps startup review/no-replay. Interrupted/damaged-only evidence cannot become an empty library/default configuration. Truly new folders remain usable. Future/ambiguous version data, access failures and cancellation remain distinct from a safe first launch. Preserve existing temporary and damaged evidence during unsuccessful writes.

No queue/settings/favorites/bundle schema version changes, account/vault changes, secret restoration, provider upgrade or native dispatch permission are introduced. The queue continues to write7/read1–7, settings/favorites/bundles retain schema1. Existing backups are not trusted as proof of a running account or destination. An original settings document lacking Version retains legacy implicit1 compatibility with explicit review feedback. Current valid files are not rewritten merely by recovery reads. Installed editions and actual user data remain outside this development increment.

Risks: accidentally blocking first launch, replaying recovered intent, selecting a backup over a valid primary, hiding unsupported future data, changing normal corrupt-file recovery, truncating preexisting `.tmp`, and replacing a different `.damaged` original. Regressions will use actual bounded local files, preserved-byte assertions, the real coordinator/Shell composition, cancellation and final packaged checks. Rollback is the preceding fixed development stage plus its verified fixture snapshot; do not downgrade real newer data. No new dependency, per-account worker, timer, native action or expanded account permission is needed. Existing serialized owners and decoded-file bounds remain in force (Rule18); this is an incremental repair under Rule20, not a store rewrite.

## Implemented and exercised

- Queue load distinguishes a genuinely new folder from a missing main with a verified backup, interrupted/damaged evidence, an unavailable file or incompatible generation. A backup loads read-only and paused. Startup converts its active intent to review and persists that decision without replay, retaining process receipt and pinned budget. A `ClientStartedUnverified` row with a valid receipt and pinned budget is already a reviewable reserving client and keeps its state, so a fresh exact PID/creation observation can reconcile it after restart (CAP-14-03). The actual Shell keeps account rows available when this separate queue cannot initialize, and shows a fixed backup-recovery notice/event when it succeeds.
- Direct queue saves cannot replace corrupt orphan backups or damaged-only recovery states with an apparently fresh queue. A valid primary remains authoritative for reads. Before rotation, unread/oversized/unknown/future backups are preserved; only a declared-supported damaged backup behind a valid primary may be replaced. New writes use owned `CreateNew` temporary files. Distinct damaged originals cannot replace the occupied preservation slot, while identical evidence permits deliberate repair. Oversized originals stay in place rather than being copied without a bound.
- Queue temporary cleanup releases its writer even when deletion fails. A controlled serializer marks its owned temporary read-only, triggers a real Windows deletion failure, verifies the original primary and retained evidence, then proves another save fails promptly on that evidence instead of hanging behind the stranded semaphore. This is an actual filesystem failure test, not a mocked cleanup result or a Roblox operation.
- Settings load/save share the existing serialized owner. Missing-primary verified backups load without rewriting, with clear feedback; truly new folders receive defaults. Temporary/damaged-only states, future primary/backup generations, access failures, cancellation and occupied distinct damaged evidence cannot silently reset preferences. The legacy missing-Version schema1 form remains accepted with a review/save notice. Optional fields/unknown existing schema1 metadata remain compatible; no credential recovery was added.
- Favorites and recipient bundles already recovered populated orphan backups; those paths remain covered. They now reject duplicate/incompatible root versions before generic record recovery. Their mutations also preserve incompatible or unreadable unused backups behind valid primaries. The two existing duplicate-Version expectations changed precisely from Damaged to UnsupportedVersion; other assertions remain.
- Bounded iterative version scans detect future/duplicate root markers before later malformed JSON or unfamiliar deep prefixes can disguise them as current corruption. Normal record decoding retains its stricter depth limits. Nested-only versions are not root authority. Queue/settings UTF-8 BOM compatibility remains. No fallback or mutation is allowed merely because an unsupported generation could not decode fully.
- The Guide explains backup review, paused intent, preserved `.bak`/`.tmp`/`.damaged` files and compatible-version recovery. No UI recovery button claims to verify a running account or restore obsolete secrets.
