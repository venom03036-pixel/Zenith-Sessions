# Saved-document authority before host execution

Cycle0.44. The preceding real interpreter/input integration passed controlled/native own-window checks; catalogv1 still identifies saved display metadata, not encrypted document bytes. Close that gap before adding execution IPC. This is one increment toward the full manager, not a replacement for qualified background input, per-target images, account/arrival/reconnect, broadcasting or sixteen-client acceptance.

## Incremental changes and compatibility

Keep IMacroDocumentStore.Save, its Load result positional constructor/deconstruction, the encrypted v2 container, macro schema3 and metadata-only catalogv1 unchanged. Add an optional ISavedMacroDocumentStore.SaveWithReceipt capability returning the actual detached prepared model plus an optional immutable receipt. Add a nonpositional optional Receipt init property to MacroDocumentLoadResult. Existing stores and Public builds retain ordinary editing/loading and metadata listing; no receipt means unavailable for saved-document resolution, never an editor-model fallback.

The receipt binds nonempty macro ID, bounded ciphertext length and uppercase SHA256 of the exact complete encrypted bytes. It means bytes successfully published/read by that call, not current-file ownership, an input grant or cross-process compare-and-swap. Save computes the receipt/result from the exact prepared model and encrypted buffer before WriteAtomic clears the ciphertext, and returns it only after replacement succeeds. Load attaches it to the same buffer it authenticates/deserializes; no extra read/decrypt is added. The existing final migrated-file verification read supplies migration's receipt. Only owned immediate canonical GetLibraryPath(ID) purpose1 `.zmacro` files with acceptable nonredirected path evidence receive receipts. External, noncanonical, backup, legacy or empty-ID files remain ordinarily usable without a receipt. SaveWithReceipt must not turn a formerly valid noncanonical save into a failure.

The Personal editor maintains a bounded host-local binding of catalog SavedRevision to internal owned path/receipt/generation, never retained MacroModel or decrypted document bodies. Actual prepared saved metadata supplies the published descriptor. Normal/generated, recording, import, migration/load, recovery and undo paths must bind the actual saved/read result; a cached deletion descriptor plus restored-file boolean is insufficient. Failed saves retain last saved display metadata, but later resolution authenticates fresh bytes rather than assuming the previous file survived.

Every actual outstanding write remains counted until its own I/O/owned completion terminates. The catalog's newest per-ID save token is insufficient: older blocked A can still write after newer B fails. Keep generation fencing and outstanding counts separately from metadata publication. A concurrent read stays Busy/Changed until all relevant writers finish. Row/write-budget exhaustion disables resolution without failing normal document saves; explicit reload cannot revive authority while older actual writers remain unfinished. Delete/reset/load/import rollback/recovery/undo/close fence readers before disk mutation. Late completions cannot resurrect a removed/reset binding.

## Host-local resolution and plan freezing

Undo keeps the existing successful move and may restore the old receipt/path only as an **unverified expected candidate**, alongside a fresh metadata revision. It does not add another synchronous100MiB read/decode to the UI command. Its normal explicit ReadAsync must freshly authenticate restored bytes, match that expected ID/receipt and recheck generations before any pin; missing receipt is Unavailable, changed bytes are Changed. Cached metadata plus a restored-file boolean never suffices. Independent review approved this lazy verification and requires an altered-restored-file regression.

Add small host-local SavedMacroReference/ReadResult/Pin/source contracts in the existing .NET8 execution library. The reference contains host session ID, macro ID and saved revision. Paths, hashes, decrypted bodies and templates do not enter metadata IPC. A pin keeps the detached authenticated read private and carries a generation/current-entry guard; fixed status text/ToString avoids accidental content logging. The Personal-only composition references this library conditionally. There is no new public execution operation or manager Run button in this increment.

For an explicit request, capture exact host/revision/entry/mutation generation under the owner lock. Perform one bounded tracked authenticated read off the dispatcher, compare its ID/hash/length with the saved binding, then recheck owner state. No lock is held across I/O or callbacks. A bounded plan preparer uses the existing real interpreter plan compiler off UI and checks the same guard after compilation, rejecting late saves, removal, reload or close. Unsupported document/target/actions remain explicit failures. The successful exact-read/guard check pins the revision for that operation: later edits affect future starts and do not mutate an already frozen plan. This is not a file lease or a promise to detect an arbitrary external edit after an already accepted pin. Every later request rereads/authenticates current bytes; replaced/missing/corrupt files never execute old cached editor content.

Keep one actual read/preparation owner, cancellation and joined disposal. Closing fences requests immediately; asynchronous editor shutdown joins actual work before shared services disappear. Never synchronously wait for a dispatcher continuation from Dispose. Caller cancellation does not free a still-running I/O slot prematurely. Public/installed products and real libraries are not exercised or modified during development.

The existing synchronous editor Dispose remains an immediate close/fence path; it does not claim to join noncancellable document I/O or add a UI-blocking wait. Personal gains IAsyncDisposable, which awaits the existing ShutdownAsync path before Dispose. Owners must keep dependencies alive until ShutdownAsync/DisposeAsync completes; MainWindow already does so. Retain the last actual reader task through its final tail, dispose its token source outside the catalog gate before releasing the slot, and keep recovery-reader tails joinable too. Tests must distinguish responsive fencing from actual asynchronous cleanup rather than claiming they are equivalent.
