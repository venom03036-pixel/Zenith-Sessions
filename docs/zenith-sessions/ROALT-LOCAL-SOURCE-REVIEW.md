## 3. Saved sign-in is an app-owned browser credential

The frontend add-account action invokes `login` (`src/features/accounts/AddAccountDialog.tsx:87–91`). `commands.rs:184–189` opens `capture_login`, then follows the add-account path; `commands.rs:159` calls `authenticated_user(0,cookie)` before encrypted storage/upsert. `roblox_api/mod.rs:91–97` routes that lookup to the fixed `users.roblox.com/v1/users/authenticated` endpoint. This is a cookie-backed saved sign-in verified against Roblox's authenticated-user response, not an OAuth grant and not an independent native installation per account. [Commands](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/commands.rs#L159-L189).

`webview.rs:55–106` creates a dedicated app-owned `webview-login`, with a global login slot, initial `about:blank`, a persistent data directory and `incognito(false)`. Hardening at `349–384` disables password saving and clears authentication cookies before injecting a selected session. The login poll at `564–601` checks the owned WebView cookie manager every 700 ms for up to 15 minutes and selects `.ROBLOSECURITY`. Navigation policy at `607` permits specified HTTPS Roblox/Google/Apple destinations. These source mechanisms do not prove complete isolation, successful browser cleanup or compatibility with all current sign-in/2FA flows. [Login and profile construction](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/webview.rs#L55-L106), [hardening](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/webview.rs#L349-L384), [poll and navigation](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/webview.rs#L564-L624).

Per-account web windows retain separate app-owned session directories (`webview.rs:215–280`). The cookie injection uses HttpOnly/Secure/Lax properties (`349–384`); on close, `commands.rs:951–980` revalidates that the cookie belongs to the same saved Roblox UserId before saving. A signed-out browser path can retain the stored cookie (`webview.rs:537`). The close callback precedes cookie clearing (`530,548`); provider-clear results are ignored at `80,278`, and a marker-creation failure is logged without failing the window creation (`109`). The bounded wait at `629` is for browser exit, not game arrival. Vault lock closes `session-*` windows with at most a five-second wait (`commands.rs:2534`); it does not establish that an in-flight `login-*` flow has been fenced. These are concrete lifecycle review points, not an executed exploit or a guarantee that a credential escaped.

## 4. Vault, rotation, deletion and export

The vault wraps secrets with zero-on-drop behavior, uses UserId-bound authenticated data, and protects a random encryption key with Windows DPAPI (`vault/mod.rs:30,51,102`). Master-password mode adds Argon2id and DPAPI (`254–266`); production KDF settings are 64 MiB, three passes and four lanes (`vault/master.rs:12`). `storage/cipher.rs:1` documents a separate DPAPI-protected key for the SQLCipher database. In DPAPI-only mode, vault `lock` is a no-op for cryptographic key availability (`vault/mod.rs:155`), which differs from the UI's operation-lock concept. Account summary fields omit the cookie (`model.rs:63–97`). [Vault](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/vault/mod.rs#L30-L155), [master derivation](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/vault/master.rs#L1-L38), [storage cipher](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/storage/cipher.rs#L1).

There is no equivalent of Zenith's durable authorization-generation compare in the traced rotation write. `roblox_api/mod.rs:649–656` sends a rotated cookie to the sink before response body/status/identity validation. `main.rs:61–67` keeps a vector of zeroizing plaintext secrets while locked and writes rotation results through `storage/mod.rs:383`; that path does not compare the previous credential incarnation. A delayed response or old browser close can therefore overwrite a newer sign-in in this source path. The pending vector has no explicit item cap at its declaration. These are stale-write and retention concerns established by control/data flow, not measured frequency, demonstrated compromise or evidence that every response rotates. [Rotation sink](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/roblox_api/mod.rs#L649-L656), [pending/write owner](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/main.rs#L61-L88), [storage update](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/storage/mod.rs#L383).

Deletion removes the database row before detached browser-directory cleanup (`commands.rs:390–403`). IDs are monotonically allocated/nonreused (`storage/mod.rs:425`); local deletion does not revoke every server-side Roblox session. Reveal/copy commands exist at `commands.rs:487` onward. Portable backup at `2597` includes protected exported cookies after reauthentication; `vault/backup.rs:1` uses portable Argon2id/AES-GCM rather than DPAPI. Those are deliberate credential-bearing utilities and differ from Zenith's current metadata-only exports. Their presence is not permission to implement bulk cookie import/export or secret reveal in Zenith.

## 5. Native launch, destinations and multi-instance behavior

Native launch uses the selected stored cookie, attempts an assertion/authentication ticket, constructs a launch URI, and starts a discovered executable (`launcher/mod.rs:147–189`, `roblox_api/mod.rs:218–236`, `launcher/uri.rs:60–70`, `launcher/client.rs:149–168`). Global discovery selects an existing client path (`launcher/client.rs:30–98`); `AccountSummary` has no per-account native installation/profile (`model.rs:67–97`). Separate browser-session directories are not separate native Roblox installations. Starting a process or obtaining a ticket is not proof of account identity, successful gameplay or requested-server arrival. [Launch](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/launcher/mod.rs#L147-L189), [client discovery/start](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/launcher/client.rs#L30-L168).

`launcher/target.rs`, `launcher/uri.rs` and `launcher/bulk.rs` separately implement places, jobs, private/share/follow resolution and staged batch work; corresponding commands and frontend API wrappers exist. An accepted requested target is not confirmed arrival. Private access and share codes carry different authority from a public PlaceId/JobId. Nothing in this static review demonstrates current support for every accepted URL or guarantees that all bulk recipients reach the same job. Zenith's bounded public parser and explicit unresolved private/share outcomes should not be widened merely because the reference parses more forms.

The source's multi-instance mechanism includes a singleton-name mutex (`instances/multi.rs:313–326`), remote-handle takeover/close (`257–280,422–452`), and exclusive locks on shared login files (`537–565`). These are enforcement/shared-state interventions, not ordinary per-account directory ownership. They conflict with the preserved Zenith boundary and were neither run nor ported. Current native compatibility and concurrency success remain unverified. [Multi-instance source](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/instances/multi.rs#L257-L326), [takeover/shared files](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/instances/multi.rs#L422-L565).

Source tests requiring real capture are ignored (`362–363,387–388`). These are identifiable costs and bounds/gaps, not a measured leak or GPU budget. [Worker and queue](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/instances/capture.rs#L42-L176), [readback](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/instances/capture.rs#L262-L313).

This frontend throttling reduces demand but does not create a backend bounded queue or fixed four-window cap. A retained image of a minimized window is not fresh minimized gameplay. Policy differences alone do not establish superior measured overhead or equivalent preview fluidity.

## 11. Network guard, QoS and other network activity

COM-scan failure logs an error and yields false, so an unknown category can allow the launch policy to proceed. [Guard](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/network.rs#L27-L149).

This is an executable-wide outbound aggregate, not per-account download control. The “applied this boot” state (`107–114`) is not a fresh readback of the actual privileged policy. No elevation or network policy change was performed here. [QoS](https://github.com/inspectsoftware/RoALT/blob/2e304a0c2c5ab90e40b63a982f81c03e992270d4/src-tauri/src/instances/qos.rs#L1-L114).

`model.rs:503–511` defaults self-update checks, Discord presence and the online counter on, while log cleaning is off. `online.rs:11–42` posts a per-launch random UUID to a Cloudflare worker every two minutes; `src/data.ts:92–95` schedules this even when the main presentation is hidden. `server/online-counter/worker.js` retains at most 50,000 IDs for five minutes and explicitly treats the count as spoofable. These literal payload/retention observations do not certify server operations or prove that no other identifying transport metadata exists.

`news.rs:13–43` concurrently fetches GitHub, DevForum feeds and a newsroom source, with a 3 MB body cap and six items per source (`67–83`); `src/data.ts:89–90` schedules news every 30 minutes. News and online counts are separate from Roblox account/game requests. Their failure must not be mistaken for lost native-session identity. ## 17. New sign-in migration decision: implementation in progress

The latest user instruction authorizes replacing the new-account OAuth flow with **manual official Roblox sign-in in an app-owned WebView2 window**, then an explicit Save action. The implementation direction is a separate `roblox-session` provider, a protected saved session credential and an authenticated Roblox user lookup binding it to the returned numeric UserId. It preserves per-profile CurrentUser DPAPI/context binding, identity deduplication, durable monotonic generations and callback/commit fences. Root implementation is in progress: this document does **not** claim the new flow has built, passed tests, signed in successfully, isolated browser state correctly or selected a native game account.

This authorization covers the owned official sign-in session. It does not cover unrelated Chrome/Edge profiles, saved passwords, pasted/bulk-imported cookies, fabricated password/2FA forms or conversion of OAuth grants into cookies. No credential may enter profile metadata, queue storage, logs, diagnostic exports or ordinary launch arguments. Legacy OAuth records remain readable for compatibility and profile preservation; they must not silently be treated as session credentials or proof of native launch authority. The browser is for authentication, not a game-in-browser fallback.

The migration is incremental rather than a replacement of all account data. Save must verify identity before committing; account switching, cancellation, Lock, Panic, disconnect and deletion must invalidate late callbacks. Generation reservations survive deletion/relink and protect against stale credentials overwriting a fresh sign-in. Explicit failure/unknown states preserve profiles and prevent successful-looking native claims. Any rollback must preserve existing profiles and protected records without automatically restoring invalidated secrets or changing the provider interpretation of an old payload.

Regression targets for the new implementation include Save after Lock/Panic/cancel, late browser close, selected-account changes, delete/relink, swapped or corrupt protected records, old payloads without current identity context, generation reuse, identity duplicates, browser-runtime absence, owned-directory cleanup failure and accidental secret inclusion in export/log/queue data. These are required checks to record when actually executed, not completed results from this source study.

Native authentication-ticket handoff, current client compatibility, supported concurrency and positively matched user/place/job arrival remain separate unavailable integrations. The reference's remote-handle closure and shared-login-file locking are not part of this migration. No reference code was reused, no real account/application was changed, and no native success or performance claim follows from the sign-in design decision.
