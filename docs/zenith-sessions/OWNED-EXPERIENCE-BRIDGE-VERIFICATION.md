# Owned Roblox experience bridge

## What the backend can do

The Windows transport publishes a short-lived status or exact public-server move command to one configured universe. The Roblox server script accepts commands only for allowlisted players and places. Status reports a player currently present at the specified source. A move pins the player, source place and job, destination place and job, and one operation ID. The destination writes its receipt only after Roblox raises the player arrival event with matching source data and the same operation claim.

Publishing, receipt at the source, teleport initiation, and arrival are distinct results. An expired request, missing receipt, older operation, or ambiguous transport failure leaves arrival unconfirmed. When a storage update, teleport or receipt step fails on the server, the script does not retry it. It writes one warning to the server log that names the step (move, status check, arrival receipt or teleport failure receipt) and carries the Roblox error text, so the creator can tell a throttle from a teleport failure or a script bug. The warning omits operation, claim and job IDs. An arrival receipt is evidence of a player at the destination server at the reported time. Windows process identity, sign-in, and permission to route local input need their own evidence. This bridge operates on connected players and cannot launch or reconnect a native client.

Each player has one receipt slot. An atomic Roblox storage update claims an operation before any move. A move occupies that slot for up to 45 seconds, including after a terminal receipt, so it is never repeated. A status check is finished once its receipt is written and does not hold the slot: a newer status check or move replaces it, so "confirm the player is at the source, then move" works straight away. The move's own receipt also shows the player was at the source, because the script moves only a player on the exact source server. After that replacement, a read for the status check reports pending, then expired. Duplicate or out-of-order commands leave the slot alone. A late source update cannot downgrade a destination arrival. A server handles up to four operations at a time, with at most one deferred terminal callback per active player. Busy servers can leave a request without a receipt. The bridge exposes that as pending or expired. For each request it ignores this way, the script writes one warning to the server log that names the step and says why: a command for that player was still running, another result for that player was already waiting, or the server was already running four bridge commands. These warnings carry no user, place, job, operation or claim ID. If Roblox refuses the command subscription when a server starts, the script writes a warning to the server log and retries after 1 second, doubling the wait up to 60 seconds, until the subscription succeeds. Commands sent before then get no receipt and also show as pending or expired.

The Windows transport allows one in-flight request, with at least one second between publishes and half a second between reads. Roblox throttling can extend those intervals. Each request has a five-second cancellation deadline, and a receipt body is limited to 4 KiB. There is no polling worker or automatic republication. A server may still finish a command after local cancellation if Roblox already received it. Receipt times come from the Roblox server's clock. The script accepts a command while that clock is up to two seconds behind the PC, so the Windows reader accepts a receipt time up to two seconds before the command's issue time. A receipt time may be at most two seconds after Roblox's own response time (the HTTP `Date` header), or after the PC's time when a response has no `Date`.

The bridge needs the Windows clock within two seconds of Roblox's. The script ignores a command issued more than two seconds after its own clock, so a PC clock that far ahead makes the server ignore commands. A PC clock behind Roblox's cuts each command's 45 seconds short by the same amount, and at 45 seconds behind the server ignores every command. Each Open Cloud response carries Roblox's time in whole seconds. When that time, allowing for the round trip and the whole-second rounding, shows the PC more than two seconds ahead or behind, a publish returns **ClockSkew** instead of Published, and a read returns ClockSkew instead of Pending. A clock off by three seconds plus the request's round trip is always reported; one off by between two seconds and that may not be, and a slow response with agreeing clocks is never reported. A genuine receipt is still reported as Acknowledged, because the server may have acted on the command. The transport does not keep the estimate between requests, so the next request after the clock is synced reports normally. A response without a `Date` header leaves today's behaviour unchanged. The server script keeps its own clock as the authority and was not changed.

The protocol keeps the existing numeric ID types and rejects IDs beyond Luau's exact integer range at this bridge boundary. It currently supports exact public jobs in the approved universe. Private and reserved access data are outside the command format.

## Setup boundary

The repository's server script ships with an empty allowlist and an unset universe. It exits in Studio and on private or reserved servers. To prepare a published acceptance trial, configure the creator-owned universe and approved place and player IDs in a private copy of the script. Install it in `ServerScriptService` on both source and destination places. Use Roblox's Creator Dashboard to provision separate API keys for publishing messages and reading receipts in the chosen universe. [Roblox messaging guide](https://create.roblox.com/docs/cloud/guides/usage-messaging) · [Roblox data store reference](https://create.roblox.com/docs/cloud/reference/features/storage)

The desktop adapter expects two callbacks that retrieve those separate keys from protected local storage. Connect those callbacks through the Personal host before enabling the bridge. Key setup and the live trial remain pending. The source tree, generated fixture and test outputs contain synthetic values. The script uses Roblox's documented server teleport and join-data mechanisms. [Roblox teleport guide](https://create.roblox.com/docs/projects/teleport) · [Roblox Player.GetJoinData](https://create.roblox.com/docs/reference/engine/classes/Player#GetJoinData)

## Executed checks

- The standalone Luau compiler compiled the shipped script. Twenty executed server cases used a controlled Roblox service substitute and the same server script with synthetic allowlists. They covered disabled defaults, input validation, the clock allowance (a command issued three seconds ahead of the server or a whole lifetime behind it is ignored; two seconds ahead is accepted), status, exact moves, duplicates, a finished status check that a later move or newer status replaces at once (an older command still cannot), arrival ordering, failure callbacks, expiry, a failed receipt write, a failed deferred receipt write, a failed command subscription that is retried with capped backoff before a status command is received, a command ignored because the player already had one running, a second waiting result for the same player, a fifth command on a server already running four, the exact move and status JSON that the Windows transport publishes, the exact receipts the script stores for those two commands (the move's arrival receipt and the status receipt, `claimId` included), and the 1024-byte message limit (1,025 bytes ignored, 1,024 accepted). Every case sends the script JSON text, so it passes through the script's size limit and decode step. The substitute for Roblox's `HttpService:JSONDecode` reads flat objects of strings, integers, true, false and null, turns null into nil as Roblox does, and rejects anything else, so it is stricter than Roblox, never looser. Failed steps are checked for one server warning each, naming the step and carrying the Roblox error but no operation or claim ID. Ignored requests are checked for one warning each that gives the reason and contains no user, universe, place, job, operation or claim ID. A clean move writes none. The 0.57 record below predates ten of these cases (the clock-allowance case among them), the warning checks and the JSON text path.
- The Windows suite reads the same move and status JSON from the embedded Luau fixture. It fails if the transport publishes different text for those commands, or if the widest command it accepts (maximum IDs and issue time, 355 bytes) would exceed the script's 1024-byte limit. It also reads the two receipt texts from the fixture and fails unless the transport reports them as Acknowledged, Arrived at the destination and Acknowledged, AtSource. A receipt field renamed or retyped on one side therefore fails one of the two suites. These goldens pin the agreed shape; how Roblox's own storage serializes a receipt still needs the live trial. When the Luau binaries are present under `artifacts/sessions-owned-bridge-0.57/luau`, the suite also runs all twenty server cases through the local verifier under Windows PowerShell 5.1; without them, that one test is reported as skipped.
- The Windows suite also covers the transport's failure mapping: a 401 or 403 answer to a publish or a read gives AuthorizationRequired, a 500 or 503 gives Unavailable, a key store that fails (at once or later) gives AuthorizationRequired without sending a request, and a request Roblox never answers ends as Unavailable at the five-second deadline and frees the lane.
- The isolated Windows launch suite passed **603 checks twice** with zero build warnings or errors. Twenty-three new cases covered the two Open Cloud routes and key separation, stages and exact IDs, malformed and oversized responses, pacing, cancellation, and unavailable credentials.
- The staged app remains **0.50.0-preview**. The Windows code and Lua script were verified using isolated synthetic data. No live Roblox response, installed client, creator project, real account, or UI participated. Live native selection, exact arrival, and reconnect remain unverified.
