# Official-page native handoff research

Reviewed November 5, 2026 Eastern / November 6, 2026 UTC; final source checkpoint approximately 00:27 UTC. Scope: `CAP-02-*`, `VA-06-*` and `CHAT-20`. All three supplied prompt fingerprints match the ledger. F §17.6 (`293–305`) and A §17.6 (`76–88`) permit a documented short-lived handoff, prohibit long-lived credentials in launch arguments/URLs/diagnostics, require fresh scheduler admission and require observed account/session verification. The latest saved-session instruction replaces the default OAuth flow; it does not authorize client modification or instance-enforcement manipulation.

**Decision:** an official-page-generated handoff is a concrete candidate worth testing. The ordinary logged-in website-to-player route and WebView2's cancellable external-scheme event are documented. Their combination has **not** been demonstrated to select a saved account correctly in Zenith, and the exact current emitted URI has not been independently captured. A dedicated, always-cancelled capture-only adapter is the next bounded step. Native dispatch remains unavailable until its separate gates pass; this is an evidence gap, not a conclusion that the route is impossible.

Only anonymous HTTPS retrieval, public documentation and supplied static source were examined. No WebView environment, sign-in, cookie store, account endpoint, authenticated request, website/reference script execution, ticket issuance, native launch, client alteration, build or test was performed. The disposable HTTP retrieval helper executed only the bounded anonymous GETs described below. Only this document was added.

## Current first-party evidence

Implementation follow-up: [0.19 adds the dedicated capture-only adapter and controlled tests](HANDOFF-PROBE-VERIFICATION.md). No actual browser or selected account was used in that increment. The research conclusions and live/native acceptance gaps below remain unchanged; the earlier next-step proposal is now code, not demonstrated native capability.

Roblox's [How to Install and Play Roblox](https://en.help.roblox.com/hc/en-us/articles/204473560-How-to-Install-and-Play-Roblox) describes logging into the website, opening an experience, selecting Play and allowing the browser to open Roblox. This establishes an ordinary official website-to-native-player workflow. It does not document third-party embedded-browser compatibility, session-cookie portability, account selection across an already running player, or simultaneous players.

The current Creator Hub [Deep links](https://create.roblox.com/docs/production/promotion/deeplinks) page documents `https://www.roblox.com/games/start?placeId=…` as web-to-app and lists optional instance/private/follow parameters. It also marks this construction process deprecated in favor of share links. Its `userId` parameter means the user to **follow**, not the account that should authenticate the player. A destination link therefore does not bind the selected saved account. [Share links](https://create.roblox.com/docs/production/promotion/share-links) are creator-generated links for owned experiences/items; the documented creation permission is not a general third-party account-selection API. Prefer an ordinary official experience page plus explicit user Play for the first experiment; treat `/games/start` compatibility as an additional observation to make.

Microsoft documents [LaunchingExternalUriScheme](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.launchingexternalurischeme?view=webview2-dotnet-1.0.3800.47) for navigations to OS-registered schemes. The host can cancel or defer the request before external dispatch. The event follows `NavigationStarting`; the associated `NavigationCompleted` reports failure/`ConnectionAborted` even when the host allows the external handoff. Neither that completion nor a shell invocation proves native success. A cross-origin frame without a user gesture may be blocked before the event is raised.

The [event arguments](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2launchingexternalurischemeeventargs?view=webview2-dotnet-1.0.3800.47) supply `Uri`, `Cancel`, `InitiatingOrigin`, `IsUserInitiated` and `GetDeferral()`. [InitiatingOrigin](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2launchingexternalurischemeeventargs.initiatingorigin?view=webview2-dotnet-1.0.3800.47) can be empty for host-initiated navigation and can represent a child frame or an opaque frame's precursor origin. It is provenance to validate, not a Roblox UserId or proof that only the main frame initiated the request. Actual origin and gesture values for Roblox's asynchronous launch flow still need observation.

Microsoft's [profile documentation](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/multi-profile-support) establishes separate cookie/cache storage by profile and supports InPrivate controller options. Its [AddOrUpdateCookie](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2cookiemanager.addorupdatecookie?view=webview2-dotnet-1.0.3800.47) method sets cookie data in the owned WebView. These host APIs make isolated session seeding technically possible; they do not promise Roblox will accept a particular saved session or carry it into the native client. No system-browser profile is required for this proposed route.

Microsoft's [WebView2 security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security) calls for validating document/message origins and restricting host objects, web messages and navigation. The proposed window needs the official page's own JavaScript to run, but needs no injected script, generic native proxy, password inspection or native API exposed to that page.

The current official documentation above was accessible, but it cannot substitute for current emitted handoff evidence.

## Smallest compatible adapter contract

The following is an independent engineering proposal, not a claim of currently supported Roblox integration.

1. **One owned operation.** Create an on-demand private WebView for one pinned profile, verified UserId, durable authorization generation, frozen requested destination and operation generation. Keep at most one browser/handoff owner, one candidate and one bounded deadline; no idle hidden browser per saved account. Do not hold a resource reservation indefinitely while a user handles a challenge.
2. **Selected session only.** Retrieve only the selected protected record just before use and seed only this app-owned context. Begin on a blank page, establish the cookie context before Roblox navigation and verify the authenticated UserId. Never use the default browser's account, old profile storage, display alias, an OAuth token or native app's current account as fallback. An expired/challenged session returns sign-in-required without starting anything.
3. **Official page owns launch preparation.** Navigate to the exact approved HTTPS Roblox experience/start page. Let the user select Play on the real page. Do not invoke private ticket endpoints, inject a replacement launcher, manufacture a native URI or replay an old one. Website sign-in/challenge/permission restrictions remain visible outcomes.
4. **Capture is cancelled first.** Register external-scheme and navigation guards before loading the page. The external handler sets cancellation synchronously for every request, then evaluates only the first candidate from the current context. Validate the top-level page, initiating origin and operation generation; reject unrelated/empty/unexpected provenance. Treat `IsUserInitiated` as additional evidence, not account authority. False/absent gesture handling for asynchronous or automatic `/games/start` must be decided from observed evidence, not silently permitted.
5. **Validate without exposing the secret.** Use a bounded parser for the observed current `roblox-player` grammar, exact allowed fields and destination endpoint/query. Reject duplicate keys, control characters, malformed/double encoding, arbitrary nested hosts/protocols, unexpected launch modes and destination mismatch. A bare destination-only `roblox://` link is insufficient evidence of selected-account handoff. Treat any opaque ticket/full URI as secret: no logs, files, journal, clipboard, exception interpolation or user-visible raw URI. Unknown current variants fail explicitly rather than being rewritten to fit a guessed format.
6. **Bind browser rotation and queued authority.** If the owned page rotates or switches its session, verify the resulting credential's UserId. A matching rotation must use the existing durable vault/projection/generation workflow; a different identity stops the operation. The queued command cannot continue with its old generation or silently adopt a new one. Resolve the new generation explicitly under the scheduler's authorization rules and recheck account binding/resources before dispatch. Failed or uncertain reconciliation produces no native handoff.
7. **One use, short local lifetime.** Hold the candidate only in a redacted disposable in-memory object, allow one consumption and reject it after a small monotonic local deadline (for example ten seconds). This is a conservative local policy, **not** a Roblox ticket-expiry guarantee. The SDK exposes the URI as a managed string; minimize copies/lifetime without claiming guaranteed memory erasure. Never persist/retry a consumed or uncertain handoff. If the official page fails or the deadline passes, require a new explicit attempt.
8. **One guarded dispatch boundary.** After fresh RAM/commit/CPU admission and a final grant/operation-generation check, dispatch only through a separately validated current registered Roblox/approved-bootstrapper handler. Missing, changed or ambiguous handler trust stops dispatch. Check cancellation at the actual side-effect boundary. Returning from shell dispatch means requested/uncertain, not a verified client or arrival; retain truthful reservation/uncertainty handling and do not automatically issue another handoff.
9. **Owned cancellation and cleanup.** Lock, Panic, Disconnect, replacement operation and disposal revoke future capture/dispatch, cancel waits and join the browser owner to terminal cleanup. Late events cannot commit rotation or launch. Already delivered OS/native work cannot be recalled. Unregister handlers, complete any deferrals, clear the owned browser session and join its exit/deletion flow; cleanup failure stays explicit. Never alter Roblox-owned login files, client locks, native memory or settings to make this route work.

Current `OwnedRobloxSignIn.cs:186–192` intentionally blocks non-HTTPS navigation and popups. Keep that sign-in boundary intact. A dedicated handoff mode needs a coordinated navigation policy: simply adding an external-scheme event while the earlier navigation handler cancels the request is insufficient. Do not broadly allow non-HTTPS navigation to obtain the event. If the required guard/runtime interface cannot be installed before navigation, keep the entire handoff mode disabled.

## Evidence needed before capability changes

- **Controlled code checks first:** parser fuzz/bounds/duplicates/encoding, wrong origin/destination, one-use/deadline, missing handler, cancellation before/after each await, late rotation/disconnect, and uncertain dispatch. These can be tested without a real account or client.
- **Owned-browser capture-only acceptance:** in a separately authorized explicit sign-in/save context, navigate to the official experience page, select Play, cancel every external event and verify actual origin/gesture/frame behavior, current URI structure and selected UserId. Retain only allowlisted field names, counts, timings and outcomes; never a live ticket, cookie or complete URI. Observe cookie rotation and actual browser cleanup. This research cycle did not perform that exercise.
- **Single native handoff acceptance:** only after the capture/validation gates, exercise one guarded dispatch and verify the actual local process identity and observed account/destination independently. Requested link fields, remote browser presence, timing and a resource-holder diagnostic alone cannot prove native UserId/arrival. A wrong-account/current-app substitution must fail visibly.
- **Separate multi-client decision:** ordinary successful browser launching does not establish multiple simultaneous clients, reconnect, background input, same-server arrival or sixteen-client capacity. The preserved platform-guidance and no-bypass gates still apply independently.

Capability labels remain separate: **CanLinkIdentity** has existing controlled saved-session evidence; **CanSelectSavedAccount in an owned website context** and **CanProducePageHandoff** are plausible but live-unverified; **CanLaunchNativeAsSelectedAccount**, **CanVerifyArrival** and **CanReconnect** are not demonstrated. **CanMultiInstance** remains independently unavailable/unverified. The next useful implementation is the capture-only adapter and its synthetic guards, followed by observed evidence—not another inferred ticket endpoint or a successful-looking native-launch button.
