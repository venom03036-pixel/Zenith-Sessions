# Shared macro assignments — 0.35 proposed design

Incrementally add durable references from an individual saved account, an independent saved group, or a recipient bundle to one Personal macro. This is a necessary shared-macro workflow, not background execution qualification. Keep 0.34's real saved-metadata connection and the existing editor/foreground/input/capture owners unchanged. Do not copy documents, templates, credentials or executable instructions into assignments. No installed application or real account is needed for implementation tests.

## Contract and persistence

Use platform-independent Sessions.Core metadata contracts: target kind Account/Group/Bundle plus nonempty stable target ID; one nonempty macro ID; bounded last-observed target/macro display names; an immutable assignment record. An opaque store generation GUID and monotonic catalog revision form a compare-and-swap stamp. These are assignment concurrency identities only, never account authentication or macro execution authority.

Use a separate `macro-assignments.db` with the existing Microsoft.Data.Sqlite dependency. Keep accounts.db schema5 and encrypted macro/container formats unchanged. Schema1 has one metadata row for generation/revision and an assignment table keyed by target kind/ID. It contains no active runs, host session/revision tokens, target handles, authorization, input queues or macro bodies. First explicit write creates storage; missing storage can load as empty only when no database/journal sidecar exists. Damaged, oversized, foreign or unsupported files fail visibly and are preserved rather than becoming an empty library.

Page at most100 assignments per request with an optional expected store stamp. Keep a bounded operational budget of10,000 assignment references and16MiB per database/sidecar; saved profiles retain no artificial product limit. Read within one SQLite transaction; either generation or revision changing during paging requires explicit refresh. The absent-store stamp is Guid.Empty/0, rechecked together with schema and metadata inside the actual writer transaction. Existing foreign/schema0 files never become a fresh store. Save/Remove require the reviewed stamp, reject concurrent writers/stale generations and advance only a real committed change. An unrelated change can require review; this conservative first version avoids ambiguous merges. Removing an already absent row is a checked no-op. Cancellation before commit rolls back. Successful commit returns definite Applied even if cancellation follows; only an actual indeterminate commit error reports outcome unknown. UI cancellation can suppress publication, but cannot imply rollback or compensate by deleting committed data.

Use a bounded serialized store entry path (four outstanding operations), finite lock/deadline waits and one tracked blocking worker per admitted operation. No timer, per-profile worker or background scan. Dispose cancels admission and joins actual work before releasing its owner. Validate schema, IDs, Unicode, lengths, page shapes, file sizes and path redirection. SQLite journaling supplies atomic commits/interrupted-write recovery; it does not promise recovery from arbitrary media corruption. Never create a replacement database over damaged or unsupported data.

Cross-file profile/group/bundle changes cannot be made atomic with this independent metadata store. Accordingly, assignment references are retained if their target disappears and displayed as last-observed hints. Renaming never changes identity; deleting/recreating a same-name group cannot adopt the old reference. No input/launch command may use assignment existence as proof of a current target. Future run-start resolution must check current authoritative targets/members, host macro ID/current saved revision, account/process identity, provider capability, input ownership and resources; it must freeze the recipients/revision then. Do not silently inherit profile assignments through multiple group memberships or choose precedence: an explicit account/group/bundle command uses that target's assignment.

## Application and interface

Add an owned MacroAssignmentsViewModel and Shell partial. The Automation page keeps the saved-macro catalog and adds a compact assignment panel with explicit target selectors: Selected account, Current saved group, Selected recipient bundle. Capture the chosen stable identity before asynchronous work; show its name/kind and explain that group/bundle membership is resolved at future start. Provide Assign selected saved macro, Refresh assignments, Previous/Next, Remove assignment with confirmation, and Stop request. Render saved assignments as recycled rows with target, macro and reference status. Empty, busy, stale, missing/unchecked target and failed persistence states are distinct. Do not label metadata as Ready to run or add a working-looking unavailable Run control.

Only a selected descriptor belonging to the current nonstale received host page can create/replace an assignment. Revalidate that captured host page/session/revision before saving. Persist the macro ID and display name, not the opaque host-generation revision. An observed failed/changed refresh invalidates the current choice; there is no persistent disconnect notification or automatic polling. An off-page ID is not reviewed, not necessarily missing. Previously saved assignments survive and require revalidation at future start. Target choices are hints about explicitly selected saved objects and are not authorization. Changing account, group, bundle, page, host selection or draft while an operation is pending must not redirect its captured request. Apply/Remove completes only for its captured target/stamp; a stale completion cannot overwrite a newer page or claim current-target validation. Lock/Panic cancel pending assignment work and fence callbacks; an already committed metadata change remains discoverable by explicit refresh. App shutdown joins actual operations. No assignment operation reads/decrypts the vault or initiates capture/input/Roblox/network activity.

Keep test fixtures injectable and use isolated temporary roots. Sample mode can exercise sample assignments but cannot contact the real macro host; an explicit owned metadata fixture may be injected for integration tests. Add concise guide text describing persistence, last-known names, refresh, removal, no auto-resume and remaining execution integration.

## Migration, risk, rollback and Rule18

This is additive; no account/credential/macro migration or dependency is required. Removing the panel/store leaves the separate metadata file available for a later compatible build. Existing installs are not changed. Main risks are stale/ABA updates, target namespace reuse, false successful saves, reentrant cancellation/disposal, unstable paging, damaged-file replacement and UI work during IO. Test strict validation, concurrent store instances, cancellation/commit boundaries, rollback, unsupported/corrupt files, path redirection, empty/no-op behavior, page generations, captured selection, late callbacks, actual SQLite reopen and end-to-end Shell/production composition. Rerun existing catalog/group/bundle/editor-adjacent regressions and exact packaged checks.

Rule18: bounded page/storage/concurrency and metadata allocations; no capture/input hot path, hidden browser, new timer, provider privilege or secret access. Disk work stays off the UI thread, errors use fixed descriptions, and actual worker lifetime is owned. Final interactive layouts, full DPI/focus/latency, actual macro execution and real account tests remain separate acceptance work. Review this design before implementing the new persistence/UI connection under Rule20.

Rule20 independent review approved this design with the four clarifications above on November6. Future execution still needs an atomic membership resolver; current per-page AccountRepository reads cannot freeze a changing group. That missing execution capability is not claimed by metadata assignment persistence.
