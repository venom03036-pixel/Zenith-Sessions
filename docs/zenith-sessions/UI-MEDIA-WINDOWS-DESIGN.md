# UI media and all-client Windows overview — incremental integration

0.36 headshots/manual gallery and0.37 all-observed Windows overview are implemented with scoped verification. See [media evidence](PUBLIC-MEDIA-VERIFICATION.md) and [overview evidence](WINDOWS-OVERVIEW-VERIFICATION.md). The design below also retains uncompleted full visual/native/performance acceptance; it is not a finished-release claim.

The latest user direction includes 16 UI concepts: retain Zenith's branding/themes while moving toward flat compact account rows and an inspector; show the saved player's actual headshot; show a rotating gallery for the chosen experience; and add a **Windows** overview that evenly tiles every observed client **inside the manager**. This overview is separate from moving native client windows. The concepts guide layout and behavior, not a replacement brand. This document records a source/documentation audit on 2026-11-06. This document began as the0.35 source audit. **0.36 now implements automatic visible-page headshots and manual ordered galleries**, with [executed evidence](PUBLIC-MEDIA-VERIFICATION.md). 0.37 implements the all-client Windows overview in the following phase with [executed evidence](WINDOWS-OVERVIEW-VERIFICATION.md). Automatic rotation and full concept-layout/native acceptance remain pending; the original audit bullets describe the pre0.36 baseline.

## What exists

- The current avatar is already a real **headshot**: [RobloxPublicDirectory](../../src/Zenith.Sessions.Windows/RobloxPublicDirectory.cs) requests `/v1/users/avatar-headshot` as a 150×150 PNG and checks the returned player ID. [PublicAccountPresentation](../../src/Zenith.Sessions.App/PublicAccountPresentation.cs) fully validates/decodes the image, retains at most 128 decoded entries, and admits one active fetch. [ShellDirectoryFeatures](../../src/Zenith.Sessions.App/ShellDirectoryFeatures.cs) exposes manual refresh and rejects late results after player/grant/context changes. Account reload attaches cache hits; it does not populate uncached avatars automatically. [MainWindow](../../src/Zenith.Sessions.App/MainWindow.xaml) binds `AccountRow.Avatar` over a fallback initial.
- [PublicRobloxGames](../../src/Zenith.Sessions.Core/PublicRobloxGames.cs), [RobloxPublicGames](../../src/Zenith.Sessions.Windows/RobloxPublicGames.cs) and [GameDetailsViewModel](../../src/Zenith.Sessions.App/GameDetailsViewModel.cs) supply experience metadata and **one square icon**. There is no gallery contract, gallery client, slide state or carousel. The existing shared avatar/icon decoder requires exactly 150×150; it must not simply accept arbitrary gallery dimensions.
- [ClientPreviews](../../src/Zenith.Sessions.Core/ClientPreviews.cs), [ClientPreviewCoordinator](../../src/Zenith.Sessions.Core/ClientPreviewCoordinator.cs), [ShellPreviewFeatures](../../src/Zenith.Sessions.App/ShellPreviewFeatures.cs) and [ClientPreviewsViewModel](../../src/Zenith.Sessions.App/ClientPreviewsViewModel.cs) pin up to four selected clients, produce at most 320×180 pixels per image, and expire images after three seconds. The UI uses fixed-width cards in a wrapping panel. This is not the requested all-client overview.
- [WindowsClientPreviewProvider](../../src/Zenith.Sessions.Windows/WindowsClientPreviewProvider.cs) owns one D3D device and one readback lane, validates PID/start/HWND/client identity, preserves the Windows capture indicator, and rejects hidden/minimized/changed clients. Its active source cache is currently limited to four; sources absent from the next batch are released. It box-filters each frame on its own D3D device (GenerateMips) and copies only the smallest mip level that still covers the output to the CPU, then samples that level; a 1920×1080 client reads back 480×270 (about 0.5 MB) instead of 8.3 MB. Drivers without automatic BGRA mips read level 0 the same way. An owned-window WGC test checks the read level and colours; native capture cadence and GPU time remain unmeasured.

## Primary Roblox evidence and remaining uncertainty

- Roblox documents [public avatar headshots and game thumbnail endpoints](https://create.roblox.com/docs/cloud/reference/domains/thumbnails). The [official thumbnail Swagger](https://thumbnails.roblox.com/docs/json/v1) lists headshot sizes, PNG output, `/v1/games/{universeId}/thumbnails` with explicit thumbnail IDs, and `/v1/games/multiget/thumbnails` with `countPerUniverse`/`defaults` and 16:9 sizes from 256×144 through 768×432. This audit made documentation requests, not real account/game requests.
- Roblox distinguishes an ordered experience-detail preview list from personalized homepage thumbnails in [its media guide](https://create.roblox.com/docs/cloud/guides/experience-icons-and-thumbnails). Its [thumbnail guidance](https://create.roblox.com/docs/production/publishing/thumbnails) describes up to ten detail-page images/videos. A generic multiget response must not automatically be called the exact ordered detail gallery.
- [The official games reference](https://create.roblox.com/docs/cloud/reference/domains/games) lists public `GET /v2/games/{universeId}/media` as Experimental; `/v1/.../media` is deprecated. Ordered media discovery followed by explicit thumbnail-ID retrieval is a prospective route. The current v2 response schema, ordering behavior and real returned image states were **not validated** here. Confirm those contracts and retain a bounded sanitized fixture before implementing their parser. Do not use authenticated editing APIs, HTML/browser scraping, arbitrary external video URLs, or credentials to obtain display media.

## Phase 1 — automatic headshots and experience gallery

1. Keep player identity sourced from the matching verified saved-sign-in summary; imported usernames/profile IDs are not identity authority. Add one shared bounded visible-row/sign-in-completion loader, deduplicated by player ID, sharing public HTTP slots, cooldowns and cache bounds. Do not launch one task/timer per account or issue a naive parallel loop against the single-active presenter. Fence row/query/grant changes, Lock and disposal. Show a neutral loading/unavailable silhouette instead of initials while an actual image is unavailable. A headshot never proves a native client's account or an active session.
2. Add a small optional gallery interface and immutable descriptors bound to requested PlaceId plus resolved UniverseId, thumbnail identity, image status and retrieval time. Never replace a requested subplace with the root place. Reject foreign/duplicate IDs and non-allowlisted image URLs; use the existing anonymous, no-redirect public transport and shared request/cache budgets. Keep the descriptor count at ten and start with validated PNG image slides; identify unsupported video entries explicitly.
3. Add a separate bounded 16:9 decoder policy, retaining the existing strict 150×150 avatar/icon path. Bound encoded bytes, dimensions, decoded pixels and retained current/next slides; force full decoding before display. No remote decoder, file stream or mutable image escapes its owner. Keep failure/empty/pending/moderated states distinct.
4. Present the chosen experience's images with previous/next, position indicators and pauseable rotation. One page-owned cadence, or the existing shared presentation tick, advances retained slides; no network fetch on every tick. Pause/clear on hidden/locked/disposed context, respect reduced-motion preferences, and discard old-destination replies. Keep the compact inspector and Zenith theme resources. Images are official experience media, not live client frames or proof of access/arrival.

## Phase 2 — Windows overview with every observed tile

Separate the **observed tile roster** from the **active capture cache**. Every observed client receives a stable tile keyed by exact PID/start/HWND, including clients with no frame, missing windows, minimized/hidden states or deferred capture. The current sampler has a 128-process operational budget and marks incomplete inventories; show that incompleteness rather than claim all Windows processes were discovered. Do not silently drop the fifth tile or substitute native-window arrangement for this view.

Use deterministic grid geometry fitted to the available manager viewport, with aspect-preserving content and a compact selected-tile inspector. One owned scheduler fairly rotates eligible targets under aggregate source-memory, retained output-pixel, readback-pixel/rate and concurrency budgets. Keep one native readback in flight. Retain only a bounded byte-budgeted active source cache; changing a four-item request currently destroys other sources, so fair scheduling also needs deliberate cache/release semantics. No per-window timers, independent loops, unbounded frame history or hidden work while the overview is off.

The present reservation formula in [ClientPreviewBufferReader](../../src/Zenith.Sessions.Windows/ClientPreviewBufferReader.cs) counts three source surfaces per active source, a largest-source drain allowance and a 64-MiB readback allowance under 192 MiB. Sixteen 1920×1080 sources would require approximately **452 MiB under that model**, before unrelated graphics allocations. This is a conservative accounting calculation, not measured residency. Removing the four-target constant alone cannot satisfy the budget. Retained output copies and frozen UI bitmaps need their own aggregate accounting.

Report each frame's actual capture time and refresh status. A sweep over many clients can exceed the existing three-second expiry: choose an explicit adaptive refresh/freshness policy, with aged-frame overlays or no-current-frame states, rather than redating cached pixels. State the achieved per-tile cadence; do not promise identical FPS for every count/window size. Preserve resource leases, exact native revalidation before/after conversion, source generations, default capture indicators, and joined cleanup. Lock/Panic/hide/pressure fence future work; unavailable clients remain visible as status tiles. No focus/input forwarding, desktop fallback, account association or automatic client restoration is introduced.

GPU downsampling before CPU readback may be a later measured improvement. The present full-size copy remains a material cost; changing frame-pool dimensions is not established scaling behavior. Review that native ownership/design separately before claiming an efficiency improvement.

## Verification and measurement

Use isolated metadata/image fixtures and fake capture providers first: reordered/foreign IDs, hostile image URLs, malformed/oversized PNGs, destination/grant changes, cooldowns, cache eviction, reentrant cancellation, joined shutdown, and theme/DPI/keyboard interaction. Prove that all observed tiles remain present while a smaller active cache rotates fairly, including PID reuse, HWND changes, denied/minimized windows, budget exhaustion and stale frames. Measure actual visited targets so a time-budget break cannot skip the same clients forever.

Measure 1/4/16/32/128 synthetic targets and owned diagnostic windows across representative source sizes: achieved cadence/fairness, capture age, CPU, managed allocations, retained output bytes, native surface/readback estimates, handle counts and stop/cleanup latency. Distinguish modeled reservations from measured process/GPU use. Real Roblox capture, overlapping-window behavior, sustained overhead and complete production UI acceptance remain deferred; this plan supplies no Roblox compatibility, performance-superiority, background-input, native-account or release-readiness proof.
