# Distribution foundations — R-shell-14 and R-shell-15

Checkpoint `0.60-d9distribution`. These are disabled-by-default release tools and controlled offline verification, **not a published installer, a production update channel, or ReleaseReady acceptance**. No real installation, registry write, shortcut, prerequisite download, sign-in, client, or paid test occurred.

## Implemented

`SignedUpdateVerifier` accepts a bounded envelope containing the exact base64 manifest bytes, key ID and fixed-width P-256/SHA-256 signature. Its domain prefix binds the signature to Zenith's v1 update format. It requires an embedded allowlisted key/publisher, product identity, newer version, ReleaseReady=true, an expiry within 90 days, package length and SHA-256. Modified bytes, unknown/retired keys, previews, rollback versions, oversized manifests and incompatible URLs fail closed.

`IUpdateFeed` has separate HTTPS and explicit local-file implementations. HTTPS has no credentials/cookies/browser identity, redirects are refused, requests time out, and the stager supplies a linked three-minute cancellation deadline through streaming reads. The signed package must share the feed's origin/transport. ZIP bytes are bounded, hashed through a handle that denies writes/deletion, then extracted into a fresh GUID child. Extraction rejects traversal, duplicate/case-colliding names, ADS, reserved Windows device names, trailing-dot/space paths and symbolic links; count, expanded total and per-file limits apply. The app EXE must pass the existing cached Windows Authenticode chain policy and match the certificate SHA-256 tied to the embedded signing key. No downloaded executable is run by staging. Failures remove only the newly owned stage when its paths remain unredirected.

`Zenith.Sessions.ReleaseTool` exposes `keygen`, `sign`, and `stage`. It is published as one framework-dependent win-x64 EXE, including managed dependencies and native extraction content; runtime/deps metadata is bundled. Its embedded `trusted-update-keys.json` is **empty**, so `stage` returns code 2 before reading a feed. The optional SDK single-file analyzer is disabled to keep offline publishing within the installed SDK/cache; no trimming is enabled. Actual single-file publish and disabled execution were checked. [Microsoft's deployment documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview) describes the bundling model.

The key-generation/signing wrappers require an explicitly selected release tool. Key generation refuses repository/redirected private-key destinations and existing outputs, uses an attended passphrase (never an argument/environment variable), and writes encrypted PKCS#8 AES-256-CBC/SHA-256 with 300,000 iterations. Public keys use SPKI base64. No production key was generated. Key custody, access permissions, offline backup and passphrase handling remain the owner's release operation; memory zeroization of managed strings is not claimed.

`Install-ZenithSessions.ps1` is an explicit, non-elevated per-user tool. It requires a configured feed and an Authenticode-pinned **single-file** release tool, retains a read lock while verifying/running that tool, and installs only its verified release stage. Destination is fixed to `%LOCALAPPDATA%\Programs\Zenith Sessions`. It checks Windows x64/build 19041, .NET 10 Desktop Runtime and Microsoft's documented WebView2 registry IDs. If missing, WebView2 is offered only after the operator types INSTALL; its bootstrapper download has byte/time bounds and must carry a valid Microsoft Authenticode signature before invocation. [Microsoft's distribution guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution) identifies the runtime registry ID and per-user behavior. No bootstrapper was downloaded or executed here.

The operator separately confirms the Zenith version/destination. Zenith must be closed (the installer never terminates it), so promotion occurs before the next application start. The promotion uses the existing stage/current/previous rename pattern, now with post-move rollback: fixed sibling paths, no redirected files, complete release hash inventory, required app/uninstaller files, and installer ownership markers. A failed final verification restores the prior app and retains the rejected stage. Existing unowned folders and interrupted/previous stages are preserved for recovery rather than erased. The install then creates a Start menu shortcut and HKCU Apps & features registration. A registration/shortcut failure can occur after files were promoted: the error remains visible and the previous app remains available; automatic shell-registration rollback is not yet implemented.

`Uninstall-ZenithSessions.ps1` only operates from the fixed owned per-user install. UNINSTALL confirms removing binaries and shell registration; a separate exact DELETE PERSONAL DATA response is required to remove `%LOCALAPPDATA%\ZenithSessions\Personal`. Otherwise all account data remains. Other Zenith editions are never selected. Retained previous/pending versions are left for manual recovery. Reparse checks run before recursive operations. Installer/uninstaller interactive Windows behavior is unverified until an attended isolated-guest trial.

The local/Actions gate also restores and publishes the single-file tool with zero warnings, and refuses external executable dependencies in that output. The six test-suite inventory and exact paid-cloud exclusion are unchanged.

## Release formats and operator preparation

Only after final release acceptance, prepare `release-manifest.json` inside the app ZIP with `FormatVersion:1`, `Product:"Zenith.Sessions.Personal"`, `Version:"a.b.c.d"`, `ReleaseReady:true`, and `Files` entries `{Path,Length,Sha256}` for **every other file**. Include both uninstaller/common scripts before computing that inventory; do not mutate a verified preview's flag to imply acceptance. ZIP entries must be files, not explicit directory entries. Sign the app EXE and the published single-file release tool with the approved Authenticode certificate; manifest hashes must describe the final signed bytes.

The update manifest signed by `Sign-ZenithSessionsRelease.ps1` has `FormatVersion`, `Product`, `Version`, `ReleaseReady`, `ExpiresUtc` (ISO UTC), `PackageUri`, `PackageBytes`, and `PackageSha256`. `PackageUri` must use HTTPS on the feed origin; local-file feeds are only for explicit tooling/fixtures. Add an audited `UpdateSigningKey` object `{Id,PublicKeySpki,PublisherCertificateSha256}` to the release tool's embedded trust resource before publishing it. Distribute the approved publisher fingerprint separately so the installer can pin the tool.

Rotation requires a release that embeds both current and replacement public keys before switching the feed to the replacement key; a subsequent release removes the retired key. A compromised key needs an independently trusted replacement distribution, not a feed instruction to trust itself. No private key or release feed is shipped. A host outage never changes installed files or blocks ordinary Zenith operation.
