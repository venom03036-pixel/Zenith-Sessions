# Distribution foundations — R-shell-14 and R-shell-15

Checkpoint `0.60-d9distribution`. These are disabled-by-default release tools and controlled offline verification, **not a published installer, a production update channel, or ReleaseReady acceptance**. No real installation, registry write, shortcut, prerequisite download, sign-in, client, or paid test occurred.

## Implemented

`SignedUpdateVerifier` accepts a bounded envelope containing the exact base64 manifest bytes, key ID and fixed-width P-256/SHA-256 signature. Its domain prefix binds the signature to Zenith's v1 update format. It requires an embedded allowlisted key/publisher, product identity, newer version, ReleaseReady=true, an expiry within 90 days, package length and SHA-256. Modified bytes, unknown/retired keys, previews, rollback versions, oversized manifests and incompatible URLs fail closed.

`IUpdateFeed` has separate HTTPS and explicit local-file implementations. HTTPS has no credentials/cookies/browser identity, redirects are refused, requests time out, and the stager supplies a linked three-minute cancellation deadline through streaming reads. The signed package must share the feed's origin/transport. ZIP bytes are bounded, hashed through a handle that denies writes/deletion, then extracted into a fresh GUID child. Extraction rejects traversal, duplicate/case-colliding names, ADS, reserved Windows device names, trailing-dot/space paths and symbolic links; count, expanded total and per-file limits apply. The app EXE must pass the existing cached Windows Authenticode chain policy and match the certificate SHA-256 tied to the embedded signing key. No downloaded executable is run by staging. Failures remove only the newly owned stage when its paths remain unredirected.

`Zenith.Sessions.ReleaseTool` exposes `keygen`, `sign`, and `stage`. It is published as one framework-dependent win-x64 EXE, including managed dependencies and native extraction content; runtime/deps metadata is bundled. Its embedded `trusted-update-keys.json` is **empty**, so `stage` returns code 2 before reading a feed. The optional SDK single-file analyzer is disabled to keep offline publishing within the installed SDK/cache; no trimming is enabled. Actual single-file publish and disabled execution were checked. [Microsoft's deployment documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview) describes the bundling model.

The key-generation/signing wrappers require an explicitly selected release tool. Key generation refuses repository/redirected private-key destinations and existing outputs, uses an attended passphrase (never an argument/environment variable), and writes encrypted PKCS#8 AES-256-CBC/SHA-256 with 300,000 iterations. Public keys use SPKI base64. No production key was generated. Key custody, access permissions, offline backup and passphrase handling remain the owner's release operation; memory zeroization of managed strings is not claimed.

`Install-ZenithSessions.ps1` is an explicit, non-elevated per-user tool. It requires a configured feed and an Authenticode-pinned **single-file** release tool, retains a read lock while verifying/running that tool, and installs only its verified release stage. Destination is fixed to `%LOCALAPPDATA%\Programs\Zenith Sessions`. It checks Windows x64/build 19041, .NET 10 Desktop Runtime and Microsoft's documented WebView2 registry IDs. If missing, WebView2 is offered only after the operator types INSTALL; its bootstrapper download has byte/time bounds and must carry a valid Microsoft Authenticode signature before invocation. [Microsoft's distribution guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution) identifies the runtime registry ID and per-user behavior. No bootstrapper was downloaded or executed here.

The operator separately confirms the Zenith version/destination. Zenith must be closed (the installer never terminates it), so promotion occurs before the next application start. The promotion uses the existing stage/current/previous rename pattern, now with post-move rollback: fixed sibling paths, no redirected files, complete release hash inventory, required app/uninstaller files, and installer ownership markers. A failed final verification restores the prior app and retains the rejected stage. Existing unowned folders and interrupted/previous stages are preserved for recovery rather than erased. The install then creates a Start menu shortcut and HKCU Apps & features registration. The installer snapshots the prior shortcut and registry value types before promotion. A registration/shortcut failure restores that snapshot and the prior app, retaining the rejected app as pending; a rollback failure explicitly requests manual recovery and preserves the folders.

`Uninstall-ZenithSessions.ps1` only operates from the fixed owned per-user install. UNINSTALL confirms removing binaries and shell registration; a separate exact DELETE PERSONAL DATA response is required to remove `%LOCALAPPDATA%\ZenithSessions\Personal`. Otherwise all account data remains. Other Zenith editions are never selected. Retained previous/pending versions are left for manual recovery. Reparse checks run before recursive operations. Installer/uninstaller interactive Windows behavior is unverified until an attended isolated-guest trial.

The local/Actions gate also restores and publishes the single-file tool with zero warnings, and refuses external executable dependencies in that output. The six test-suite inventory and exact paid-cloud exclusion are unchanged.

## Release formats and operator preparation

`New-ZenithSessionsReleasePackage.ps1 -Source <verified-preview> -Version <a.b.c.d> -OutputDirectory <new-folder> [-ReleaseToolPath <single-file-tool>]` checks the exact preview inventory, rejects unexpected files/user-data extensions, copies into a new folder outside the source, checks the copied hashes, adds the installer scripts and selected tool, and generates `release-manifest.json`, `package.zip` and `package-evidence.json`. ZIP entries are files, with bounded count/lengths. The default is **ReleaseReady=false**. Nothing is uploaded or installed. After release acceptance and Authenticode signing, an explicit `-ReleaseApprovalFile` must identify FormatVersion=1, ReleaseReady=true, the exact Version, SourcePreviewManifestSha256, and approved PublisherCertificateSha256. Both the app and single-file release tool must match that publisher. This operator approval is not inferred from passing fixtures, and the final signed inventory describes the signed bytes.

The update manifest signed by `Sign-ZenithSessionsRelease.ps1` has `FormatVersion`, `Product`, `Version`, `ReleaseReady`, `ExpiresUtc` (ISO UTC), `PackageUri`, `PackageBytes`, and `PackageSha256`. `PackageUri` must use HTTPS on the feed origin; local-file feeds are only for explicit tooling/fixtures. Add an audited `UpdateSigningKey` object `{Id,PublicKeySpki,PublisherCertificateSha256}` to the release tool's embedded trust resource before publishing it. Distribute the approved publisher fingerprint separately so the installer can pin the tool.

Rotation requires a release that embeds both current and replacement public keys before switching the feed to the replacement key; a subsequent release removes the retired key. A compromised key needs an independently trusted replacement distribution, not a feed instruction to trust itself. No private key or release feed is shipped. A host outage never changes installed files or blocks ordinary Zenith operation.

## Apply-boundary integrity follow-up

Review found that the local stage could be changed during the installation confirmation: replacing a DLL and rewriting its unsigned local inventory made the original promotion routine accept both. `promotion-before.trx` records that exact regression failing (the altered synthetic release was incorrectly installed). The installer now opens read/delete-denying handles on the tool and every stage file, re-pins the tool, and invokes its embedded-trust `verify-stage` command immediately before copying. That command rechecks the ECDSA envelope, signed ZIP hash/length, every staged file against its corresponding signed archive entry, absence of unsigned extras, and the app publisher. It returns the digest of the inventory bytes in the signed ZIP. Promotion requires that digest before and after copying while the source handles remain held. The mutable local inventory alone can no longer authorize a DLL replacement. `promotion-after.trx`: 31 passed, zero failed/skipped, including both the reproduced substitution and real cryptographic archive revalidation fixture. The WebView2 bootstrapper also stays under a read/delete-denying handle from signature verification through its process start/wait. Same-user malware with arbitrary write/control of the app's process is not claimed to be contained by this mechanism.

## Application ownership and final offline increment

Cycle `0.60-d9distributionfinish` adds `ReleaseUpdateSession`, a disabled-by-default owner with one coalesced check, serialized atomic state writes and an optional tracked daily timer. It persists the last attempted check, so failures cannot spin; a pending release suppresses redundant daily downloads. Panic and Lock cancel the current check and pause automatic checks until an explicit check or reconfiguration. Disposal cancels and joins the timer and current check. `ReleaseToolUpdateBackend` pins/locks the packaged tool, limits its output, enforces a four-minute check deadline, cancels and terminates only its own helper on failure, and drains both output tasks; an unconfirmed helper termination remains an explicit failure. Staging has a two-GiB retained budget and validates the bounded ZIP central-directory header before allocating its entry collection.

`ShellViewModel.ReleaseUpdates` is the UI binding contract: FeedUri, PublisherCertificateSha256, CheckDaily, Status, IsChecking, PendingVersion, InstallOnNextStart; Save, CheckNow, ApproveNextStart, CancelApproval, DiscardPending and Stop commands. The integrated Settings page now exposes these commands in a collapsed section using existing theme styles; the owner's overall layout is preserved. The presentation binding regression failed before wiring and passed afterward (ROUND4-INTEGRATION-VERIFICATION.md). Attended visual and signed-update acceptance remain. DiscardPending only removes a direct GUID-named update child with its marker, refuses redirection/potential account or macro data, and never removes installed or previous app versions. Retained previous/pending installations remain a deliberate manual recovery boundary: the installer refuses replacing them.

An idle queue is required to approve next-start installation. `PendingReleaseUpdateHandoff` consumes that approval once, asks again before opening the attended installer, passes exact parent PID/start time, and exits before the installer proceeds. The installer waits at most ten seconds for that exact process; it never kills Zenith. Declining keeps the staged update for later review. The installer independently stages and reverifies the feed and asks for the actual version before applying. Sample-profile and self-check launches never offer installation. A missing release tool/installer reports the issue and opens Zenith normally.

## Stop precedence review

Independent review found two update-owner gaps: a delayed settings save could clear a newer Panic/Lock pause after its old check drained, and persisted daily settings could start work while the shell was locked at startup. `update-stop-before.trx` reproduces both with a held fake backend and manual clock: backend calls incorrectly increased from one to two after Panic, and from zero to one during locked initialization. Configuration now captures a stop generation and only resumes if no later stop occurred; every automatic/manual check also consults the current shell availability policy at admission and after the presentation callback. The signed helper checks cancellation immediately before launch. `update-stop-after.trx`: 12 update-owner tests passed, including both corrected regressions. No real helper or network was used.
